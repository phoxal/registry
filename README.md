# phoxal/registry

The Phoxal static Cargo registry. It distributes **official executable
packages** of the `phoxal/framework` train as source packages, and nothing else.

- Index: `sparse+https://phoxal.github.io/registry/`
- Generated by [margo](https://github.com/integer32llc/margo); served by GitHub
  Pages straight from `main`. There is no registry server and no publish
  endpoint.
- Browse the crates it holds at <https://phoxal.github.io/registry/>.

The four library crates - `phoxal`, `phoxal-api`, `phoxal-bus`, `phoxal-macros` -
are **not** here. They stay on crates.io. Cross-registry dependencies point one
way: packages here depend on those crates.io libraries at the exact train
version, never the reverse.

See [organization#951](https://github.com/phoxal/organization/issues/951) for
the design this implements.

## Consuming it

Nothing needs to be configured in a robot project. The `phoxal` CLI injects the
index for its own `cargo install` invocations:

```
cargo install --registry phoxal --config 'registries.phoxal.index="sparse+https://phoxal.github.io/registry/"' ...
```

Reads are anonymous; no token exists and none is needed.

## Publishing

**Publication is CI-owned and one-way.** The framework release workflow packages
each executable with `cargo package`, runs `margo add`, commits, and lets Pages
deploy. Nothing is published by hand.

Two rules hold without exception:

1. **Versions are immutable.** A version, once published, is never overwritten,
   re-uploaded, or `margo rm`'d. An incorrect train is superseded by a new patch
   train. This repository's git history is the audit trail, which only works if
   history is append-only.
2. **Nothing here is published to crates.io.** Executable packages declare
   `publish = ["phoxal"]`, so an ordinary `cargo publish` cannot reach crates.io
   by accident.

The publish workflow enforces rule 1 by refusing any `.crate` path that already
exists. If you are reading this because that check failed, the answer is a new
patch train, not a force-push.

## Layout

| Path | What it is |
|---|---|
| `config.json` | registry endpoint description Cargo reads first |
| `ph/ox/<crate>` and friends | the sparse index. Cargo's own prefix layout, at the repository root: `<c1c2>/<c3c4>/<name>` for names of four characters or more, and `1/`, `2/`, `3/<c>/` for shorter ones. One file per crate, one JSON line per version. |
| `crates/<c1c2>/<c3c4>/<name>/<version>.crate` | the published source packages |
| `index.html`, `assets/` | the human-browsable crate listing margo generates |
| `margo-config.toml` | margo's own settings; `base_url` must match the Pages URL |

The index living at the root, rather than under an `index/` prefix, is Cargo's
sparse-registry convention: `config.json`'s `dl` template and the index paths
are both resolved relative to the base URL. Anything that is not one of the
metadata files above is index content, which is how the immutability workflow
tells them apart.
